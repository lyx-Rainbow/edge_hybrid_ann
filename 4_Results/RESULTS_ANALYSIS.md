## 一、构建阶段内存分析

> 数据来源: `memory_components/memory_yfcc100m_small.json`

### 1.1 各阶段内存变化

在 yfcc100m_small（50K 向量, d=192）上，对 Curator 索引构建过程的 5 个关键阶段进行组件级内存快照：

| 阶段 | RSS (MB) | 索引内存 (MB) | 主要变化 |
|------|----------|---------------|----------|
| 训练前 | 123.24 | 0.003 | 仅根节点 (1 node, 2.8 KB) |
| 训练后 | 130.46 | 3.22 | 树展开至 1185 节点 (1.09 MB)；Bloom Filter 分配 (2.23 MB) |
| 添加向量后 | 189.51 | 40.98 | 原始向量缓冲 38.4 MB；Flash 索引 3.2 MB；ID 分配器 3.36 MB |
| 权限授予后 | 189.51 | 46.15 | 短列表 6.77 MB（含 hash 开销与 vid payload）；tenant 分配器 |
| Flush 后 | 158.71 | 12.79 | 原始向量缓冲释放；PQ 编码 3.2 MB + 码本 0.20 MB 生成 |

```
RSS (MB)
200 ┤          ╭──────────╮
180 ┤          │ 189.5    │  添加向量后 / 权限授予后
160 ┤          │          │        ╭──── 158.7  Flush 后
140 ┤    ╭─────┤  130.5   │        │
130 ┤    │ 训练后         │        │
120 ┤────╯ 123.2          │        │
     ┴     训练前         │        │
```

**关键观察**:
- **构建期峰值在"添加向量后"阶段**（RSS 189.51 MB），主要由 `raw_vectors_buffer` 贡献（38.4 MB = 50K × 192 × 4 bytes，即全精度向量暂存）。
- **Flush 将索引内存从 46.15 MB 降至 12.79 MB**，降幅 72.3%：全精度向量写入 Flash 磁盘后释放，替换为压缩的 PQ 编码。
- 训练阶段开销较小（+7.2 MB RSS），主要是树节点与 Bloom Filter 的创建。

### 1.2 Flush 后组件级内存分解

索引稳定态（Flush 后）总内存 **12.79 MB**，各组件如下：

| 组件 | 大小 (MB) | 占索引内存比 | 说明 |
|------|-----------|-------------|------|
| Shortlists (overhead + payload) | 6.77 | 52.9% | hash table 开销 (1.42 MB) + 实际 vid 数据 (5.35 MB) |
| Vector ID Allocator | 3.36 | 26.3% | vid 分配器内部映射表 |
| PQ Codes | 3.20 | 25.0% | 50K × 64 bytes（M=64, nbits=8，每向量 64 字节） |
| Flash Index | 2.42 | 18.9% | vid → buffer_offset 映射 |
| Bloom Filters | 2.23 | 17.4% | 1185 节点的 BF 位数组 |
| Tree (nodes + centroids) | 1.09 | 8.5% | 节点属性 (0.18 MB) + 质心向量 (0.91 MB) |
| Vector Indices (leaf) | 0.57 | 4.5% | 叶子节点向量索引 |
| PQ Codebook | 0.20 | 1.5% | 64 × 256 × dsub floats |

### 1.3 不同数据集规模下的索引内存

| 数据集 | 向量数 | d | 索引内存 (MB) | 每向量内存 (bytes) |
|--------|--------|---|---------------|---------------------|
| yfcc100m_small | 50K | 192 | 12.79 | 268 |
| yfcc100m | 800K | 192 | 242.33 | 318 |
| arxiv | ~1.6M | 384 | 478.69 | ~314 |

**观察**:
- yfcc100m_small 到 yfcc100m（16 倍向量数），索引内存增长 18.9 倍（12.79 → 242.33 MB），略高于线性，因为树结构和短列表等固定开销随数据量摊薄有限。
- arxiv (d=384) 相比 yfcc100m (d=192) 维度翻倍，索引内存约翻倍 (478.69 vs 242.33 MB)，主要来自质心存储翻倍。
- 内存正确性验证中，yfcc100m 和 arxiv 的查询峰值 RSS 均与索引自报内存完全吻合（差异为 0），表明 `get_total_memory_bytes()` 的统计覆盖了所有常驻组件。

## 二、查询耗时分析

> 数据来源: `query_profile/query_profile_yfcc100m_small.json`（C++ 内部 50 次查询 profiling）  
> `Curator/curator_yfcc100m_small.json`（Python 端 500 次查询 benchmark）

### 2.1 总体查询性能

yfcc100m_small, 500 queries, k=10, search_ef=1024:

| 指标 | 值 |
|------|-----|
| 平均延迟 (Python wall-clock) | 16.01 ms |
| P50 延迟 | 9.93 ms |
| P95 延迟 | 44.63 ms |
| P99 延迟 | 73.25 ms |
| QPS | 62.45 |
| 平均召回率@10 | 0.9986 |

P50 与 P95 相差约 4.5 倍，P99 高达 73 ms，存在明显的长尾延迟。

### 2.2 查询步骤耗时分解

C++ 内部 profiling（50 次查询，不含 Python/SWIG 开销）:

| 步骤 | 平均 (ms) | P50 (ms) | P95 (ms) | 占 C++ 总耗时比 |
|------|-----------|----------|----------|-----------------|
| Beam Search | 0.010 | 0.009 | 0.020 | 0.1% |
| Frontier Search | 2.478 | 2.344 | 4.168 | 24.8% |
| PQ Table Build | 0.018 | 0.016 | 0.032 | 0.2% |
| PQ Distance Compute | 2.327 | 2.211 | 3.897 | 23.3% |
| Exact Distance Compute | 0.000 | 0.000 | 0.000 | 0.0% |
| Candidate Merge | 0.057 | 0.046 | 0.141 | 0.6% |
| **Rerank (ADC)** | **7.489** | **5.250** | **11.392** | **75.0%** |
| **C++ 总计** | **9.980** | **7.875** | **15.499** | **100%** |

```
Rerank (ADC)         ██████████████████████████████████████████████████████████████████████ 75.0%
Frontier Search      ████████████████████████ 24.8%
PQ Distance Compute  ███████████████████████ 23.3%
Candidate Merge      █ 0.6%
PQ Table Build       ▏ 0.2%
Beam Search          ▏ 0.1%
```

**关键发现**:
1. **ADC Rerank 是查询延迟的绝对主导因素**，占 C++ 内部耗时的 75%。当前 `pq_rerank_topk_factor=4` 意味着对 top-40 候选向量逐一进行 ADC 精确重排序，每个候选需 M×ksub 次查表累加。
2. **Frontier Search + PQ Distance Compute 合计占 48.1%**：Frontier 从优先队列弹出节点并扫描短列表获取候选 vid；PQ Distance 对候选向量计算近似距离。两者耗时接近，说明短列表扫描与 PQ 查表开销大致相当。
3. **Beam Search / PQ Table Build / Candidate Merge 三项合计 < 1%**，开销可忽略。
4. **Exact Distance Compute = 0**，确认此配置下未触发任何精确 L2 计算，所有距离均走 PQ/ADC 路径。

### 2.3 按选择率分桶

| 选择率区间 | 查询数 | 总耗时 (ms) | Rerank (ms) | Frontier (ms) | PQ Dist (ms) |
|-----------|--------|------------|-------------|---------------|-------------|
| [0.0004, 0.0403) | 15 | 8.08 | 6.23 | 1.83 | 1.73 |
| [0.0403, 0.0803) | 7 | 9.55 | 6.74 | 2.80 | 2.63 |
| [0.0803, 0.1202) | 11 | 7.63 | 4.98 | 2.64 | 2.45 |
| [0.1202, 0.1601) | 7 | 9.14 | 5.41 | 3.72 | 3.48 |
| Overflow (>0.1601) | 10 | **16.30** | **14.12** | 2.17 | 2.06 |

**观察**:
- **Overflow 桶延迟显著偏高**（16.30 ms，是其他桶的 1.7-2.1 倍），完全由 Rerank 时间暴增（14.12 ms）导致。Overflow 查询的选择率更高 → 更多向量进入短列表 → rerank 候选集更大。
- 正常选择率范围内 (0.0004-0.1601)，总耗时相对稳定 (7.6-9.6 ms)，Frontier Search 和 PQ Distance 随选择率增大而缓慢上升，Rerank 波动较小。

### 2.4 C++ 内部耗时 vs Python Wall-Clock 耗时

| 计时方式 | 平均耗时 | 说明 |
|----------|----------|------|
| C++ profiling (50 queries) | 9.98 ms | `high_resolution_clock`，仅 C++ 内部逻辑 |
| Python benchmark (500 queries) | 16.01 ms | `perf_counter`，含 SWIG 编组 + numpy 转换 + Python 调用栈 |

差额约 **6 ms (60%)**，主要由 Python/C++ 边界开销（SWIG 类型编组、numpy array 转换）和样本量差异导致。

## 三、构建耗时分析

> 数据来源: `build_time_correct/curator_yfcc100m.json`

### 3.1 构建阶段耗时分解

yfcc100m (800K 向量, d=192)，nlist=32, PQ_M=64, PQ_nbits=8:

| 阶段 | 耗时 (s) | 占比 |
|------|----------|------|
| train (聚类训练) | 4.46 | 6.7% |
| create (索引创建) | 8.76 | 13.1% |
| grant_access (权限授予) | 10.05 | 15.1% |
| **pq_train_encode (PQ 训练+编码)** | **42.40** | **63.6%** |
| flash_write (Flash 写入) | 1.03 | 1.5% |
| **总计** | **66.70** | **100%** |

```
PQ 训练+编码  ██████████████████████████████████████████████████████████████ 63.6%
权限授予      ███████████████ 15.1%
索引创建      █████████████ 13.1%
聚类训练      ███████ 6.7%
Flash 写入    █ 1.5%
```

**分析**:
- **PQ 训练+编码是构建的绝对瓶颈**（63.6%）。此阶段调用 FAISS ProductQuantizer 对 800K 个 d=192 向量训练码本 (M=64, ksub=256) 并逐条编码。PQ 编码总量为 800K × 64 bytes = **51.2 MB**。
- Flash 写入仅需 **1.03 s**，说明磁盘顺序写入速度充足。将 PQ 码一并持久化到磁盘（与 Flash 数据文件放在同一 `disk_cache_prefix` 目录）预计增加 < 2 s，对总构建时间影响 < 3%。
- 构建前后 RSS: 1079.8 MB → 1658.4 MB，增量 578.6 MB。索引自报 242.3 MB，差额约 336 MB 为构建过程临时内存（含 `raw_vectors_buffer` ~614 MB 在 Flush 前释放，与 FAISS 内部临时分配的叠加）。

### 3.2 PQ 码外存预期收益

| 指标 | 全内存模式 (当前) | 外存模式 (预期) |
|------|-------------------|-----------------|
| PQ 编码内存 | 51.2 MB | 0 MB（或可选 LRU 缓存 ~1 MB） |
| 索引总内存 (yfcc100m) | 242.33 MB | ~191 MB |
| 内存降幅 | — | **~21%** |
| 查询延迟影响 | 基准 | 预计 +5-30%（取决于存储介质与缓存命中率） |
| 召回率 | 基准 | 完全一致（PQ 码数据不变） |
| 磁盘增量 | 0 | 51.2 MB + 32 B header |

对于 arxiv (~1.6M 向量, d=384)，若采用 M=24, nbits=8，PQ 编码为 1.6M × 24 = 38.4 MB，外存后索引内存可从 478.69 MB 降至约 440 MB。

### 3.3 内存正确性验证

| 数据集 | 查询峰值 RSS | 索引自报内存 | 差异 |
|--------|-------------|-------------|------|
| yfcc100m (800K) | 242.33 MB | 242.33 MB | 0 MB |
| arxiv (~1.6M) | 478.69 MB | 478.69 MB | 0 MB |

两数据集上 RSS 与索引自报内存**完全吻合**，验证了 `get_total_memory_bytes()` 对各组件的统计是准确且完整的。这为 PQ 外存后的内存缩减验证提供了可靠基线。

## 四、关键发现与优化方向

### 4.1 Rerank 占查询耗时 75% → 优先优化目标

当前 ADC Rerank（`rerank_topk_factor=4`，对 top-40 重排序）占 C++ 查询时间的 75%。优化方向：
- 降低 `rerank_topk_factor`（如 4→2），rerank 候选数减半，预计 C++ 总耗时下降约 35-40%，召回率损失预计 < 0.5%
- 对 Rerank 循环使用 SIMD 加速（AVX2/AVX-512 批量查表累加）
- Overflow 查询的 Rerank 耗时 (14.1 ms) 是正常桶的 2-3 倍，可针对高选择率查询单独调整 rerank 策略

### 4.2 PQ 训练+编码占构建耗时 63.6% → 外存集成代价低

Flash 写入仅需 1.03 s，磁盘 I/O 不是瓶颈。将 PQ 码持久化集成到 `finalize_flash_storage()` 中，在 Flash 写入后顺序追加 PQ 码文件，预计增加 < 2 s（< 3% 构建时间）。

### 4.3 原始向量缓冲是构建期最大内存消费者

50K 向量的 `raw_vectors_buffer` 占 38.4 MB（构建期索引内存的 93.6%）。对 800K 数据集，此缓冲约 614 MB。若需降低构建峰值内存，可分批添加向量并分批 Flush。

### 4.4 短列表占 Flush 后索引内存的 52.9%

短列表（hash table 开销 + vid payload）是索引稳定态的最大组件。若需进一步压缩内存，可考虑：
- 调整 `max_sl_size` 限制单短列表容量
- 对短列表 payload 使用紧凑编码（如 varint 压缩 vid）

### 4.5 组件级内存统计存在 ~6.5 MB 差异

Flush 后各组件之和 (~19.9 MB) 与 `get_total_memory_bytes()` (~13.4 MB) 存在差异，可能源于 Flash Index 映射表和 ID Allocator 在不同统计路径中被重复计入。建议审查 `get_memory_breakdown()` 中各字段与 `get_total_memory_bytes()` 的对账逻辑。
