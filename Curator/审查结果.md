### TODO-1: `RunningList::batch_insert()` 中 break 是否导致不完整有序？

**位置**: [common.h:196](Curator/src/common.h#L196)

```cpp
if (vids_tmp.size() == static_cast<size_t>(capacity)) break;
```

**解答**: **不会导致正确性问题。**

`batch_insert` 对两个升序输入（现有 `dists/vids` + 新 `cands`）做两路归并。由于两个输入皆是升序，归并过程从最小元素开始逐对比较取较小者，前 `capacity` 个即是全局最小的 `capacity` 个。break 后方元素必然更大，丢弃是正确的。

但有一个边界细节需确认：当 `dists` 还不满 capacity（`dists.size() < capacity`）时 break 会不会提前退出？不会——此时 `vids_tmp.size()` 达不到 `capacity`（它受限于两个输入的总元素数），所以 break 不会在不满 capacity 时被错误触发。

快捷判断逻辑 `cands[0].first < dists.back()`（line 182）也是正确的——若第一个候选的距离已大于当前列表最大距离且列表已满，则所有候选都不可用。

**结论**: 正确。可加一行注释说明 break 的安全性。

### TODO-2: `IdAllocator` 的 `free_list`、`label_to_id`、`id_to_label` 含义

**位置**: [common.h:241](Curator/src/common.h#L241)

| 变量 | 类型 | 含义 |
|------|------|------|
| `free_list` | `std::unordered_set<IntLabel>` | 记录**已释放但可复用**的内部 ID。`free_id()` 释放后将 ID 加入此集合，供后续 `allocate_id()` 复用 |
| `label_to_id` | `std::unordered_map<ExtLabel, IntLabel>` | Ext→Int 正向映射：给定外部 label（如 tenant_id=48），查找对应的稠密内部 ID |
| `id_to_label` | `std::vector<ExtLabel>` | Int→Ext 反向映射：以内部 ID 为 vector 下标 O(1) 查找外部 label。使用 `vector` 而非 `unordered_map` 是因为内部 ID 是稠密分配的 |

`free_list` 存在的原因是：tenant ID 会被临时分配给 filter index，之后被清除。若不回收 ID，每建一次 filter 就分配新 ID → 内部 ID 空间单调增长 → `id_to_label` vector 无限扩增。`free_list` 实现空洞复用，保持 ID 空间紧凑。

**结论**: 不需要修改。建议为这三个成员变量添加上述注释。

### TODO-3: `IdAllocator::allocate_id()` 逻辑详解

**位置**: [common.h:263](Curator/src/common.h#L263)

该函数实现了**空闲列表（free-list）分配器**模式：

```
allocate_id(label):
  if label 已存在 → 报错（防止重复分配）
  if free_list 非空 → 复用被释放的 ID（取一个出集合）
  else             → id = id_to_label.size()   // 分配新 ID
                     id_to_label.push_back(INVALID_ID)  // 占位哨兵
  label_to_id[label] = id
  id_to_label[id] = label       // 覆盖占位哨兵
  return id
```

`id_to_label.push_back(INVALID_ID)` 先占位的原因是：后续 `id_to_label[id] = label`（line 261）通过下标赋值，需要该位置已存在。`INVALID_ID` 作为哨兵在 `get_label()` 中被检测（line 304）。

**结论**: 正确。这是标准的 ID 分配器模式。

### TODO-4: `search_one()` 中 temp index cache 的含义和优先级

**位置**: [curator_index.cpp:378](Curator/src/curator_index.cpp#L378)

**完整调用链**:

```
外部调用 build_filter_index(predicate, qualified_vids, n)
  ├─ 分配新 tenant ID (filter_tid)
  └─ if use_temp_index_caching:
       ├─ build_temp_index(root, sorted_vids, ...) → temp_nodes
       └─ 缓存: temp_indexes_[filter_tid] = temp_nodes
               qualified_cache_[filter_tid] = sorted_vids

之后外部调用 search(query, k, filter_tid)
  └─ search_one(query, k, filter_tid)
       └─ get_cached_temp_index_data(filter_tid, ...) → 命中!
            └─ search_temp_index(temp_nodes, qualified_vids, ...)  ← 快速路径
                 （跳过主聚类树的 beam + frontier + PQ 搜索）
```

**为什么优先 temp index cache**: 临时索引只包含 qualified 向量的子集，搜索空间远小于完整聚类树。命中后直接走轻量级的 `search_temp_index`，跳过 `beam_search` → `PQ distance table` → `Frontier search` 完整链路。

**缓存未命中的情况**: 标准单租户查询（直接按 tenant_id 过滤）不会命中——它们的 tid 是真实 tenant ID，不是 filter label。只有 `build_filter_index` 创建的 filter_tid 才会命中。

**结论**: 设计正确。建议在 `get_cached_temp_index_data` 上方添加注释说明这是 bitmap filter 搜索的优化路径。

### TODO-6: temp index 的 beam search 与 frontier search 区别

**位置**: [temp_index.cpp:151](Curator/src/temp_index.cpp#L151)

两者是**两阶段互补搜索策略**，不是替代关系：

**Phase 1 — Beam Search**（lines 109-147）:
- 沿树下降，每层保留 top-`beam_size`（默认 2）个最佳节点
- 展开保留节点的子节点，不达标的丢弃到 frontier
- 终止条件：抵达无子节点 或 节点覆盖向量数 ≤ `search_ef`
- **纯导航功能**：只决定"探索哪些节点"，不收集向量

**Phase 2 — Frontier Search**（lines 153-180）:
- 优先队列按质心距离升序弹出节点
- 对每个节点展开子节点（继续探索）
- 对"终止节点"收集其覆盖的所有 qualified 向量（`[node.start, node.end)` 范围）
- **收集功能**：从 beam search 确定的优先区域 + 其竞争节点中收集候选

**为什么 beam search 不收集**: beam 只保留 2 个节点/层，大量有希望的节点被丢弃到 frontier。若此时收集，会错过这些节点覆盖的高质量向量。先 beam 导航定位最优区域，再 frontier 从该区域向外扩展收集，是正确的策略。

**结论**: 设计正确——这是一种 beam + priority-queue hybrid 搜索策略。

### TODO-7: temp index 为什么不用 `node_score()` 函数

**位置**: [temp_index.cpp:113](Curator/src/temp_index.cpp#L113)

`TempIndexNode` 不包含 `RunningMean variance` 字段（设计目标是轻量级静态结构）。而 `node_score()` 的公式是：

```cpp
float node_score(const TreeNode* node, const float* x, size_t d, float var_boost) {
    float dist = l2_sqr(x, node->centroid.data(), d);
    if (var_boost == 0.0f) return dist;  // ← temp_index 的 var_boost 恒为 0
    return dist - var_boost * static_cast<float>(node->variance.get_mean());
}
```

temp index 搜索中 `var_boost=0`（line 102），`node_score` 退化等价于 `l2_sqr`。当前直接使用 `l2_sqr` 是正确的且更清晰的——不需要假借 `node_score` 之名。

**结论**: 不需要修改。当前 `l2_sqr` 调用等价于 `node_score(node, x, d, 0.0f)`。

## 二、潜在问题深度分析

### 🔴 问题 #1: `search_temp_index` 使用节点质心距离替代真实向量距离

**位置**: [temp_index.cpp:174-177](Curator/src/temp_index.cpp#L174-L177)

**严重程度**: 高（影响 bitmap filter 查询召回率）

#### 精确影响分析

`search_temp_index` 的"收集"阶段（lines 168-178）在遇到终止节点时收集所有 qualified 向量并插入 RunningList。问题是：**每个 vid 使用的距离 score 是该节点的质心距离，不是 vid 对应向量的真实距离。**

具体场景：一个 `TempIndexNode` 覆盖 `[start=100, end=228)` 共 128 个 vids，其质心距离为 `score=12.5`。这 128 个 vid 全部以 `distance=12.5` 插入 RunningList。但实际向量距离可能分布在 `[10.2, 18.7]` 的范围。这导致：
1. **排序错误**：实际距离 10.2 的 vid 和实际距离 18.7 的 vid 在 RunningList 中位置相同
2. **低召回**：真实最近邻可能因所在节点的质心距离偏大而被挤出 top-K
3. **距离值无意义**：`results.dists[i]` 返回的数值不是真实 L2 距离，后续 rerank 等依赖距离绝对值的逻辑被破坏

#### 当前另一次生问题：frontier search 中的重复收集

`search_temp_index` lines 153-179 的逻辑同时做了两件事：展开子节点 + 收集向量。当一个父节点满足终止条件时：
- 它收集了 `[start, end)` 范围的全部 vids
- 它又把子节点推入 frontier
- 子节点出队后也会满足终止条件（它们是父范围的子集），再次收集相同的 vids

**正确做法**：满足终止条件的节点应**只收集、不展开子节点**；不满足的节点应**只展开子节点、不收集**。使用 `if-else` 而非顺序执行。

#### 精确修复方案

遵循 REFACTOR_PLAN §4.6a 的"参数化向量访问"设计原则——不将 `PQCodec` 直接传入（会破坏星型依赖），而是使用回调模板。

**Step 1: 修改 `temp_index.h` 接口**

**Step 2: 修改 `search_temp_index` 实现（temp_index.cpp）**

核心改动在 frontier search 阶段。原代码（lines 153-180）替换为：

```cpp
// Frontier search: pop nodes, either collect vids OR expand children
while (!frontier.empty()) {
    auto [score, node_idx] = frontier.top();
    frontier.pop();

    const auto& node = nodes[node_idx];

    bool is_terminal = node.children.empty() ||
                       (node.end - node.start) <= static_cast<int>(search_ef);

    if (is_terminal) {
        // ★ 终止节点：收集向量（调用回调获取真实距离），不展开子节点
        std::vector<int_vid_t> node_vids;
        node_vids.reserve(node.end - node.start);
        for (int i = node.start; i < node.end; i++) {
            node_vids.push_back(qualified_vecs[i]);
        }

        std::vector<std::pair<float, int_vid_t>> node_dists;
        compute_distances(node_vids, node_dists);  // ★ 回调到 CuratorIndex
        std::sort(node_dists.begin(), node_dists.end());
        results.batch_insert(node_dists);
    } else {
        // ★ 非终止节点：只展开子节点，不收集向量
        for (int child_idx : node.children) {
            const auto& child = nodes[child_idx];
            float child_score = l2_sqr(query, child.centroid, d);
            frontier.emplace(child_score, child_idx);
        }
    }
}
```

// 改为与 build_temp_index 的终止条件一致：

### 🔴 问题 #2: `FlashStore` fseek offset 的跨平台安全性

**位置**: [flash_store.cpp:39,50,74,115](Curator/src/flash_store.cpp)

```cpp
// write_vector:     line 39:  std::fseek(fp_, static_cast<long>(offset), SEEK_SET)
// write_leaf_region: line 50: std::fseek(fp_, static_cast<long>(region_start), SEEK_SET)
// read_vector:      line 74:  std::fseek(fp_, static_cast<long>(offset), SEEK_SET)
// read_batch:       line 115: std::fseek(fp_, static_cast<long>(sorted[i].first), SEEK_SET)
```

**严重程度**: 中（目标平台 WSL-Ubuntu 64-bit 上实际安全，但代码不够健壮）

#### 精确平台分析

**在 WSL-Ubuntu 24.04 + GCC 13.3 + x86_64 上**:

| 类型 | 大小 | 最大值 |
|------|:--:|------|
| `long` | 8 字节（64-bit） | 9.2 × 10^18 |
| `size_t` | 8 字节（64-bit） | 1.8 × 10^19 |
| `off_t`（`_FILE_OFFSET_BITS=64` 默认启用） | 8 字节 | 9.2 × 10^18 |

**最大 flash 文件偏移量计算**（arxiv 完整版，最坏情况）:
```
leaf_region_size_ = max_leaf_size × d × sizeof(float)
                  = 128 × 384 × 4
                  = 196,608 bytes

num_leaves ≈ ceil(1,600,000 / 128) ≈ 12,500

max_offset  = num_leaves × leaf_region_size_
            ≈ 12,500 × 196,608
            ≈ 2,457,600,000 bytes ≈ 2.46 GB
```

2.46 GB < 2^63（9.2 EB），所以在 64-bit `long` 上 `static_cast<long>(offset)` **不会截断**。在 x86_64 Linux 上，glibc 的 `fseek` 实际上通过 `_FILE_OFFSET_BITS=64` 宏自动映射到 `fseeko`（接收 `off_t`），即使显式声明 `long` 也无问题。

**但是**：如果代码被移植到以下平台，截断就会发生：
- 32-bit ARM Linux（`long` = 4 字节，`LONG_MAX` ≈ 2.14 GB）
- Windows MSVC（`long` = 4 字节，即使 x86_64 目标）

对于 yfcc100m（800K×192×4≈614MB）和 sift1m/gist1m（1M×128/960×4），文件均 < 2GB，不受影响。但 arxiv 完整版（2.46GB）在 32-bit `long` 平台上会越界。

#### 精确修复方案

**方案选择**：`pq_block_cache.cpp` 已在用 `pread`（line 48, 261），保持仓库内 I/O 风格一致。将 `fseek+fread/fwrite` 统一替换为 `pread/pwrite`。

### 🔴 问题 #3: K-means `n_clusters > n` 时导致越界读取

**位置**: [kmeans.cpp:48](Curator/src/kmeans.cpp#L48) → [cluster_tree.cpp:65-70](Curator/src/cluster_tree.cpp#L65-L70)

**严重程度**: 中（稀有触发条件，但触发即 UB）

#### 精确触发场景还原

需要同时满足两个条件：
1. `n > cfg.max_leaf_size`（否则 `build_tree` 提前返回）
2. `n < cfg.n_clusters`（否则 kmeans 不需要截断）

**可触发示例**:
| max_leaf_size | n_clusters | n | 触发？ | 说明 |
|:---:|:---:|:---:|:---:|------|
| 128 | 64 | 50 | ❌ | `50 ≤ 128` → build_tree提前返回 |
| 64 | 128 | 100 | ✅ | `100 > 64` 且 `100 < 128` → kmeans截断→OOB |
| 32 | 64 | 50 | ✅ | `50 > 32` 且 `50 < 64` → kmeans截断→OOB |
| 128 | 64 | 200 | ❌ | `200 ≥ 64` →无需截断→安全 |

触发条件发生在 `max_leaf_size` 较小而 `n_clusters` 较大，且 `n` 恰好落在两者之间（`max_leaf_size < n < n_clusters`）。

#### 精确越界路径追踪

```
kmeans(n=100, n_clusters=128)
  └─ line 48: n_clusters = 100 (截断!)
  └─ result.centroids.resize(100 * d)  // 100*d 个 float
  └─ return result  // centroids 只有 100 个聚类的质心

回到 build_tree (cluster_tree.cpp:65-70):
  for clus_id = 0 ... 127:  // ★ 循环 cfg.n_clusters=128 次!
      clus_id=0...99:   OK — centroids[clus_id * d] 在有效范围
      clus_id=100...127: OOB — centroids[100*d ... 127*d-1] 超出 vector 范围!
```

cl_id=100 时，`result.centroids.data() + 100 * d` 指向 `centroids[100*d]`，但 `centroids` 只有 `100 * d` 个元素（下标 0..100*d-1）。`TreeNode` 构造函数中 `centroid.assign(centroid_ptr, centroid_ptr + d)` 会读取 `d` 个越界 float。

#### 精确修复方案

在 `build_tree` 中，紧接现有 guard 后增加 n_clusters 检查：

```cpp
// cluster_tree.cpp:30-33 当前代码:
if (n <= cfg.max_leaf_size || node->level >= MAX_TREE_DEPTH) {
    return;
}

// ★ 紧接其后添加:
if (n < cfg.n_clusters) {
    return;  // 向量不足，无法合理分裂为 n_clusters 个分支
}
```

**正确性验证**:

| 检查 | 作用 |
|------|------|
| `n <= max_leaf_size` | 保护小叶子节点 |
| `level >= MAX_TREE_DEPTH` | 保护深度溢出 |
| `n < n_clusters` ★new | 保护向量不足时进入 kmeans 导致截断 |

三条 guard 的组合覆盖了所有边界情况。添加后，`kmeans` 的截断逻辑（line 48）变为死代码（对 `build_tree` 路径），但保留它不影响 PQ 子空间训练路径的安全性（PQ 训练中 `n`（全量向量数）远大于 `ksub_=256`，截断不会触发）。

**额外验证 — `n=0` 的场景（空聚类子节点）**:

kmeans 返回后，某些聚类可能分配 0 个向量。此时 `build_tree(child, 0, ...)` 被调用：
- line 18: `centroid.empty()` 为 false（TreeNode 构造时已从 kmeans 质心初始化）→ 跳过均值计算，无除零
- line 31: `0 <= max_leaf_size` → **立即返回**，不进入 kmeans
- `child` 被 push 到 `node->children`，维持 invariant

空聚类子节点拥有有效的 kmeans 质心，`vector_indices` 为空，不会参与搜索。这是正确的行为。

**修改文件**: `cluster_tree.cpp`（+3 行）

### 问题 #5: PQ 训练中 OpenMP 嵌套并行效率

**位置**: [pq_codec.cpp:63-73](Curator/src/pq_codec.cpp#L63-L73)

`train()` 使用 `#pragma omp parallel for` 在外层并行 M 个子空间的 kmeans 训练。**当前是安全的**（`train` 和 `encode_all` 在 `flush()` 中顺序调用，非嵌套），但效率并非最优：

- M=128 个子空间，每个 fork/join 内部 kmeans 又做 `n_threads` 路并行
- 每次迭代 fork/join 开销 × 128 次 = 可观的线程调度开销
- 更优策略：在外层串行（或少量并行），让 kmeans 内部充分并行

**建议**: 在 `train()` 开始处添加 `omp_set_nested(0)` 禁用嵌套并行，或将外层 `parallel for` 改为普通串行循环（128 次 kmeans 顺序执行，每次 kmeans 内部充分并行）：

```cpp
// pq_codec.cpp train():
// 选项 A: 如果 n 很大（全量训练），内层充分并行即可
for (size_t m = 0; m < M; m++) {  // 串行
    auto result = kmeans(...);     // 内部 n_threads 并行
    ...
}

// 选项 B: 如果 n 适中，外少量并行 + 内串行
#pragma omp parallel for schedule(dynamic) num_threads(std::min(M, 4))
for (size_t m = 0; m < M; m++) { ... }  // + kmeans内部检测in_parallel并串行
```

选项 A 最简单且通常最优（kmeans 内已在向量级别并行）。

**修改文件**: `pq_codec.cpp`（~3 行改动）

### 问题 #6: ADC Rerank 未使用批量 I/O

**位置**: [curator_index.cpp:510-512](Curator/src/curator_index.cpp#L510-L512)

```cpp
for (size_t i = 0; i < n_rerank; i++) {
    float exact_dist = compute_vector_distance(x, cand_vectors.vids[i]);
    exact_list.insert(cand_vectors.vids[i], exact_dist);

```

每次调用 `compute_vector_distance` → `flash_.read_vector(offset, ...)` → `fseek+fread`（或修复后的 `pread`）。`n_rerank = k × rerank_topk_factor`，典型值 10×4=40 次 I/O。`FlashStore::read_batch` 已实现合并读取（lines 83-127），但此处未使用。

**修复**: 收集所有 offset，调用 `read_batch`:

```cpp
// 收集 offsets
std::vector<size_t> offsets;
std::vector<int_vid_t> rerank_vids;
for (size_t i = 0; i < n_rerank; i++) {
    int_vid_t vid = cand_vectors.vids[i];
    auto leaf_it = vid_to_leaf_id_.find(vid);
    if (leaf_it != vid_to_leaf_id_.end()) {
        auto seq_it = leaf_node_id_to_seq_.find(leaf_it->second);
        if (seq_it != leaf_node_id_to_seq_.end()) {
            auto local_it = vid_to_local_idx_.find(vid);
            if (local_it != vid_to_local_idx_.end()) {
                offsets.push_back(seq_it->second * leaf_region_size_ +
                                  local_it->second * cfg_.d * sizeof(float));
                rerank_vids.push_back(vid);
            }
        }
    }
}

// 批量读取
std::vector<float> rerank_vecs;
flash_.read_batch(offsets, cfg_.d, rerank_vecs);

// 计算距离
for (size_t i = 0; i < rerank_vids.size(); i++) {
    float exact_dist = l2_sqr(x, rerank_vecs.data() + i * cfg_.d, cfg_.d);
    exact_list.insert(rerank_vids[i], exact_dist);
}
```
